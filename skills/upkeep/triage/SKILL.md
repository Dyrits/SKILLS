# Triage

Move tasks on the configured tracker through a small state machine of intake roles. Triage acts on remote records or local intake task bodies; unresolved proposals in `documentation/capabilities/<capability>/draft.md` have no role.

If the tracker treats external pull requests as a request surface, triage covers them too. A PR is a task with attached code, using the same roles and states, with the differences noted below. Resolve a bare `#42` to an issue or PR through the tracker configuration.

## Document and tracker contract

Call the Skill tool with "document" before updating project documents; its terms (authorized, obligation, lazy, pointer) and rules apply throughout. Read the relevant requirements, specifications, working state, and backlog when present.

Read `documentation/agents/issue-tracker.md` and `documentation/agents/triage-roles.md`. If either is missing, tell the human to run `/setup-ai-workspace` and stop. This user-invoked skill cannot invoke setup itself.

"Comment", "apply a role", and "close" resolve through the tracker configuration:

- Remote operations use the platform's actual commands and labels. A local title/link reference to a published remote task does not duplicate remote role state.
- Local task bodies use `Category:` and `Status:` near the top. Comments append under `## Comments`. Rejection closes intake with `Status: not-planned`. Delivery progress, blockers, and acceptance evidence can be recorded in the body separately from intake state.

Remote comments, role changes, and closing need authorization from the maintainer's explicit triage request or confirmed outcome. A generic local document edit grants no remote publication authority. Maintain specifications, active work, and the changelog locally within scope. Candidate deferrals follow documentation's configured backlog authority; do not create a local queue beside a remote backlog.

Every comment or new task posted during triage starts with:

```markdown
> *This was generated by AI during triage.*
```

## Roles

Category roles:

- `bug`: something is broken.
- `enhancement`: new feature or improvement.

Intake-state roles:

- `to-evaluate`: maintainer needs to evaluate.
- `on-hold`: paused on a named reply, dependency, or blocker.
- `ready`: fully specified, with a brief attached, safe to pick up.
- `not-planned`: closed without action, reason recorded.

These states answer whether work is actionable. In-progress, review, and deployed state belong to the tracker's own delivery fields, local task progress, a branch, or a PR.

A ready brief can identify work a human must implement and the reason it cannot be delegated, such as access, judgment, or manual testing. This is a line in the brief, not another role. For a PR, ready means the next step on its diff is specified, whether an agent finishes it or a human merges it.

Each triaged task carries exactly one category and one state. If states conflict, flag them and ask the maintainer before acting. The role file maps canonical roles to the project's actual strings; use that mapping instead of creating duplicate vocabulary.

Normally, an untriaged task enters `to-evaluate`, then moves to `on-hold`, `ready`, or `not-planned`. A hold returns to `to-evaluate` when its named condition arrives. The maintainer can override; flag unusual transitions and confirm them first.

## Invocation

The maintainer runs `/triage` and describes the request:

- "Show me anything that needs my attention."
- "Let's look at #42."
- "Move #42 to ready."
- "What's ready for agents to pick up?"

## Show what needs attention

Query the configured tracker and show three buckets, oldest first:

1. Untriaged tasks, with no state role.
2. `to-evaluate` tasks.
3. `on-hold` tasks whose named condition has arrived. Check notes for the reply, merged dependency, or closed blocker before surfacing them.

When PRs are in scope, tag entries `[PR]` or `[task]`. Discovery includes external PRs only, using the configuration's author filter; an explicitly named PR is triaged regardless of author. Show counts and a one-line summary per item, then let the maintainer choose.

## Triage a task or PR

1. **Gather context.** Read body, comments, roles, author, dates, and prior triage notes; for a PR, also read the diff. Explore with the domain glossary and applicable architecture decision records. Search for an existing implementation by domain concept and report where you looked. Read `documentation/out-of-scope/*.md` when present and surface matching prior rejections.
2. **Recommend.** Present a category and state with reasoning and a relevant codebase summary, including any already-implemented behavior. Wait for direction.
3. **Verify.** Before refinement, reproduce a bug from the reporter's steps. For a PR, check the diff against its claims and run relevant tests or commands. Report confirmed behavior with its code path, failure, or insufficient detail. Insufficient detail supports an on-hold recommendation.
4. **Refine if needed.** Call the Skill tool twice, for "refine" and "model-domain". Resolve questions with the human one round at a time. Keep unresolved proposals in `draft.md`, incorporate agreed behavior/design/acceptance into `specifications.md`, and update domain terms and architecture decision records as decisions land.
5. **Apply the confirmed outcome:**
   - `ready`: post an [agent brief](AGENT-BRIEF.md). It is the authoritative task-execution contract, linked to canonical specifications and applicable requirements. State any reason the work needs a human.
   - `on-hold`: post notes naming exactly what the hold waits on. Keep candidate deferrals in the authoritative configured backlog: local bodies for local tracking, approved remote updates for remote tracking. Pending publication and active paused work belong in local `documentation/work-in-progress.md`, not in a competing backlog or copied tracker status.
   - `not-planned`, already implemented: close with a link to the existing implementation. This is not a rejection and does not enter the rejection knowledge base.
   - `not-planned`, rejected bug: explain politely and close.
   - `not-planned`, rejected enhancement: create or update the [out-of-scope record](OUT-OF-SCOPE.md), link it in a comment, then close.
   - `to-evaluate`: apply the role and optionally record partial progress.
6. Update relevant local context and the root changelog through documentation's shared rules. Report the outcome and any next action.

## Quick state override

If the maintainer requests a state directly, trust their decision. Confirm the role changes, comment, or closing before acting, and skip refinement. If moving to ready without a refinement session, ask whether they want an agent brief. This explicit override does not pretend a missing brief exists.

## On-hold template

```markdown
## Triage Notes

**What we've established so far:**

- Resolved fact or decision

**Waiting on:** the concrete reply, dependency, or blocker that must arrive

**What we still need (@reporter):**

- Specific, actionable question
```

Capture resolved questions so later sessions do not repeat them. Name the hold precisely enough to check whether it has lifted without rereading the whole thread.

## Resuming

Read prior notes, outstanding answers, and relevant active-work context. Check whether the named hold has lifted and present an updated picture before continuing. Reuse resolved answers instead of asking again.
