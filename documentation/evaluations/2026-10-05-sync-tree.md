# 2026-10-05 sync-tree

Written 2026-10-05 (UTC). Runs took place on 2026-10-05.

## Result

The nine behavior evals were run once each, in throwaway Git repositories. Eight met every expectation; one met two of three (32 of 33 expectations met). The three trigger and no-trigger evals selected correctly in a selection simulation. The stop rules, the compare-and-set update, and the rebase path held up. The one miss exposes an unclear rule: what counts as a "temporary branch" when the target is not named.

## Method

**Behavior evals (simulated runs, real Git).** Each runner built its scratch repositories with the setup script, read the skill and the `rebase` skill from the repository (the Skill tool was not used), and ran real Git commands inside the scratch directory. The scratch repositories have no remote, so no push was possible. Where a skill step asks the user, the runner stopped and wrote the question as its final message.

**Trigger and no-trigger evals (selection simulation).** One subagent named the first skill it would invoke for 11 shuffled, unlabeled messages across three skills. It tests the description against the other installed skills, not a live firing.

Highlights, from the runners' final Git state:

- Evals 2, 7: the runner stopped without stashing, committing, resetting, or switching; `main` did not move.
- Eval 3: stopped with three options (rebase recommended, replace `main`, stop) and both commit IDs plus the destination-only commit; `main` unchanged.
- Eval 4: `git update-ref refs/heads/main <source> <observed target>`, both checkouts untouched, ref re-read and equal to the source.
- Evals 5, 6: reported as a no-op and as already landed, with no ref moved.
- Eval 11: rebased onto the pinned `main`, fast-forwarded with `update-ref`, hotfix still in the history of `main`.
- Eval 12: the rebase stopped on an add/add conflict, was left in progress (no abort, no reset), `main` untouched, and the report named the state, the reason, and the next move.

**Eval 8, the miss.** The message names no target and says the task branch "does not exist in the original". In linked worktrees refs are shared, so it does exist there. The runner followed the skill text ("default to the source branch's name only when it identifies the corresponding branch unambiguously"), took the source name as the target, found source and target equal, and then asked whether to land on `main`, offering `git merge --ff-only`. The question, the offer of `main`, and the absence of any update match the expectations. The first expectation (do not default to `worktree/csv-export` in the original) is not met as written. Either the skill should say how a temporary branch is recognized, or the expectation and its premise should change. Nothing was edited in this run.

## Limits of the evidence

- One run per eval, no baseline, one model, and the grader is the session that edited the skills.
- Runners performed the steps by reading the skill and `rebase`, not through the Skill tool.
- Runners noted two gaps no expectation covers: `sync-tree` does not say whether `rebase`'s report-and-ask step is skipped when the user has already chosen rebase (the runners skipped it and its push step), and `rebase`'s undo advice does not account for a rebased commit already written to `main`.
- The scratch repositories have no checks, so "run the checks" was untested.

## Not run

Live trigger firing in a harness; a separate-clone (non-worktree) scenario; a network remote or push.
