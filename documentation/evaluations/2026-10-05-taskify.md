## Method

**Behavior evals (simulated runs).** Each runner read the skill and the `document` skill from the repository (the Skill tool was not used), built a scratch project containing the fixture, and wrote any task files only under that scratch project. No tracker was configured and no `gh` or network call was made; eval 6, which authorizes publishing, asked for the commands to be shown, not run. Where the skill asks for approval, the runner stopped and wrote the question as its final message.

**Trigger and no-trigger evals (selection simulation).** One subagent named the first skill it would invoke for 11 shuffled, unlabeled messages across three skills. It tests the description against the other installed skills, not a live firing.

## Limits of the evidence

- One run per eval, no baseline, one model, and the grader is the session that edited the skills.
- Evals 6 and 7 say the breakdown "is approved" without supplying it, so the runners had to reconstruct one. Eval 7 says "four of them independent"; the runner's graph made two tasks ready first and four independent after the first task, and said so.
- The fixture declares its own path as `specification.md`, while the shared documents name the file `specifications.md` ([`PROJECT-DOCUMENTS.md`](../../skills/reference/document/PROJECT-DOCUMENTS.md)). Every runner noticed the mismatch and kept the fixture's name. The fixture or the document convention should change. Resolved 2026-10-06: the fixture now declares `specifications.md`; the runs above used the earlier name.
- A runner confused `document` (in `reference/`) with a workflow skill; the skill's path is correct, so this is a runner slip, not a defect.
- Whether published issue bodies should carry body-level `Blocked by` lines next to native links is not stated (eval 6).

## Not run
