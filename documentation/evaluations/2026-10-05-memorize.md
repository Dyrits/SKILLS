## Result

The four behavior evals were run once each. Two met every expectation; two did not (13 of 15 applicable expectations met). The three trigger evals and the two no-trigger evals were checked only as a skill-selection simulation, and all five selected correctly. The run shows the current text can be followed and routes lessons to the right home. It does not show a regression-free change: there was no baseline, and each eval ran once.

Two things remain open: the reason for a glossary decision has no place to live (eval 3), and idempotence of the pointer was never exercised (eval 5).

## Method

**Behavior evals (simulated runs).** Each runner received the skill's file path and the user message, and was told to read the skill and any skill it calls from the repository, not to use the Skill tool, and to work only in a scratch directory. Where the skill names a home outside the project (the harness memory, the global scriptbook), the runner used a stand-in under `scratch/home/`. Where the message describes existing state, the runner built the smallest neutral fixture. Expectations were withheld from the runners.

**Trigger and no-trigger evals (selection simulation).** One subagent received all 11 trigger and no-trigger messages of this run's three skills, shuffled and unlabeled, and named the skill it would invoke first for each. This tests whether the description wins against the other installed skills. It is not a live firing in a harness.

No real memory, instruction file, or remote was touched.

**Eval 3.** The runner read `GLOSSARY.md` first, updated the existing `Task` entry with `_Avoid_: Ticket`, called `model-domain` (read from the repository), and wrote the lesson in one home. It did not record the reason ("the tracker already uses it"): the glossary format holds definitions only, and the runner judged the choice too easy to reverse for an architecture decision record. The saved record and the final message therefore carry no reason, which the expected output asks for. This is a tension between `memorize` (lesson with its reason) and `model-domain` (definitions only, record only hard-to-reverse decisions). Counted as not met.

**Eval 4.** The preference went to the stand-in harness memory as one file with its reason plus one index line. No project file changed. The index-line expectation applies only when `~/.agents/memory/` is used, which it was not.

**Eval 5.** The pointer was appended once to `CLAUDE.md`, after a grep found none, and a second grep confirmed a single copy. The runner did not run the skill a second time, so "running it again adds no second copy" is untested.

**Eval 6.** The key was filed nowhere (a grep of the scratch directory found no hit), the runner said secrets stay out of every home, and the non-secret URL went to `AGENTS.md` with a note that the key lives outside the repository.

## Limits of the evidence

- One run per eval, no baseline against the previous text, one model. A pass shows the text is followable, not that it improved anything.
- The runners read the skill by path. A real harness injects the skill through the Skill tool and its description listing, which was tested only by the selection simulation.
- Runners reported ambiguities that no expectation covers: where in `CLAUDE.md` the pointer goes; whether the pointer applies when the lesson goes to another home such as `GLOSSARY.md`; the line "without `document`, wait until the user installs it" on a route that never needs `document`; and whether a non-secret value pasted next to a secret should be filed at all (eval 6).
- The grader and the author of the skill changes are the same session.

## Not run

Live trigger firing in a harness; a second invocation of the skill for idempotence; the description optimizer.

**Limits.** One run each, same session as grader, no baseline.
